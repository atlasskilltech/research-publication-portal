# Supabase → MySQL migration guide

**Status (2026-11-04):** the code migration is complete and verified **locally**
on MariaDB 10.4, with **no Supabase dependency**. The target is the **shared cPanel
database `atlasuniversitye_employment_survey`**, and every RPP table, index and
constraint is prefixed `research_` (§2). **That database has NOT been inspected or
migrated yet**: its credentials are not on the development machine, and
production migrations need your explicit approval (§6). Nothing has been
committed, pushed or deployed.

---

## 1. Audit checklist (what Supabase did → what replaces it)

| Area | Supabase implementation | MySQL implementation | Files |
|---|---|---|---|
| Client init | `@supabase/ssr` + `supabase-js` (server, browser, middleware, service-role clients) | One `mysql2` pool (UTC, strict mode, parameterized) | `lib/db/core.mjs`, `lib/db/index.js`, `lib/db/tables.mjs` (removed: `lib/supabase/*`) |
| Registration | `auth.admin.generateLink({type:"invite"})` + `handle_new_user` trigger | `generateLink()` creates the unverified, passwordless, **non-admin** user plus a single-use token in one transaction | `lib/authServer.js`, `lib/repos/users.mjs`, `app/api/register/route.js` |
| App-number validation | unchanged (server-side UAT API, fail-closed) | unchanged; duplicate check via a unique key on `applicationNo` | `lib/studentCheck.js` |
| Email verification | `verifyOtp({token_hash})` | `verifyOtp()` consumes the SHA-256-hashed token exactly once (conditional UPDATE) | `lib/auth/store.mjs`, `app/auth/confirm/actions.js` |

| Sessions + cookies | Supabase JWT + refresh cookies, refreshed in middleware | `research_sessions`: SHA-256 token hash, absolute expiry (7 d), idle timeout (3 d), revocation, purpose, account-status check | `lib/auth/store.mjs`, `lib/session.js` |

| RPC functions (12) | plpgsql (revision, re-review, decisions, volume/issue, schedule/update/publish) | Same checks, row locks, `RPP:<CODE>` errors and audit rows, one MySQL transaction each | `lib/services/workflow.mjs`, `lib/decisionService.js` |

| Signed URLs | none (downloads were already streamed by authorised routes) | unchanged | `app/api/papers/[id]/manuscript`, `.../revisions/[round]/manuscript`, `app/api/public/publications/[id]/manuscript` |

**Dependencies removed:** `@supabase/ssr`, `@supabase/supabase-js`.
**Added:** `mysql2` (DB), `@node-rs/argon2` (Argon2id, prebuilt binaries),
`bcryptjs` (verifies legacy bcrypt hashes only), `jose` (Google ID-token
signature verification).
**Environment variables no longer used:** `NEXT_PUBLIC_SUPABASE_URL`,
`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`,
`SUPABASE_ACCESS_TOKEN`.
**Historical SQL:** the Postgres migrations and email templates are kept for
reference in `docs/legacy-supabase/`, outside the active migration workflow.

## 2. MySQL schema (shared cPanel database)

**Target database:** `atlasuniversitye_employment_survey` on `65.1.118.10`. It is
shared with the Employment Survey. RPP never creates a database and never reads,
alters or drops any table outside its own list. Following the shared-database
convention, every RPP table starts with **`research_`**, and so does every index,
unique key, foreign key and CHECK constraint
(`research_<table>_<what>_{idx|uq|fk|ck}`). Names are defined once, in
`lib/db/tables.mjs`, and everything else imports them.

| Migration | RPP tables (18) |
|---|---|
| (runner) | `research_migrations` (migration history: filename, applied_at) |
| `001_auth` | `research_users`, `research_sessions`, `research_user_roles`, `research_auth_tokens`, `research_user_identities`, `research_oauth_states` |
| `002_workflow` | `research_papers`, `research_paper_authors`, `research_paper_manuscripts`, `research_paper_assignments` (reviewer and editor assignments), `research_paper_activity`, `research_reviews`, `research_revisions`, `research_editorial_decisions` |
| `003_publication` | `research_volumes`, `research_issues`, `research_publications` |

There is no separate `research_reviewers` table. Reviewers (and editors) are rows
in `research_paper_assignments` with role `PEER_REVIEWER` / `DESK_REVIEWER` /
`EDITOR`, and the reviewer *capability* is a row in `research_user_roles`.
Splitting them would duplicate the double-blind and assignment rules.

- **Engine and encoding:** InnoDB, utf8mb4 (`utf8mb4_unicode_ci`), DATETIME(3) in
  **UTC**. Every pooled connection runs `SET time_zone='+00:00'` and a strict
  `sql_mode`.
- **Constraints:** 32 foreign keys, unique keys for every rule MySQL can express,
  and CHECK constraints on rounds, scores, the review-completeness rule, page
  ranges and publication completeness. JSON columns hold lists and objects.
- **Rules without a portable index:** "one open revision per paper" and "one
  corresponding author" are enforced inside transactions under
  `SELECT … FOR UPDATE`.
- **MariaDB note:** MariaDB implicitly adds a table-scoped
  `CHECK (json_valid(col))` named after each JSON column. MySQL 8 does not.
  These are the only unprefixed object names, and they can't collide with
  another application.

**Collision safety.** Each migration declares the tables it owns.
`npm run db:migrate` runs a **read-only preflight** before anything else:
- If any table a pending migration would create already exists without having
  been created by RPP's own history, it stops and changes nothing.
- An existing `research_migrations` must have the expected shape.
- Other `research_*` tables that RPP doesn't own are reported and left
  untouched.

Status mode is strictly read-only. The history table is created only by
`--apply`, after the preflight passes. The integration suite exercises all of
this against simulated Employment Survey tables: collision refused with nothing
created, foreign tables and rows byte-for-byte unchanged.

**Compatibility.** The runner refuses servers older than MySQL 8.0.16 / MariaDB
10.4. It is verified on MariaDB 10.4; **MySQL 8 is not yet tested**.

**Rollback.** `npm run db:migrate -- --rollback 003 --yes` (then 002, then 001)
works only in reverse order and only while those RPP tables are empty. It never
touches any other table. Full rollback means restoring the backup.

## 3. Authentication architecture

- **Passwords:** Argon2id (m=19 MiB, t=2, p=1). Legacy bcrypt (original MySQL app,
  Supabase export) verifies and is re-hashed on the next login. Unknown accounts
  run a dummy verification, so response timing reveals nothing.
- **Sessions:** a 256-bit random cookie `rpp_sid` (httpOnly, SameSite=Lax, Secure
  in production). MySQL stores only its SHA-256. A session is valid only if it
  is not revoked, not past its absolute expiry, not idle, has the right purpose,
  and the account is ACTIVE. Logout revokes the session. A password change or
  reset revokes **all** of the user's sessions, and so does deleting the account
  (cascade).
- **Purposes:** APP (normal), SETUP and RESET (30 minutes, accepted only by the
  password pages).
- **One-time tokens:** 256-bit hex values in the email link, stored as SHA-256,
  single use, TTL 24 h (invite) or 1 h (reset). Issuing a new token invalidates
  the older ones.
- **CSRF:** SameSite=Lax cookies, plus the middleware's same-origin check on every
  mutating request to `/api/*` and `/auth/*`. Server actions also carry Next's
  built-in origin check.
- **RBAC:** identity and roles come only from MySQL through the session.
  `isAdmin` mirrors the `ADMINISTRATOR` role atomically. Nobody can change their
  own roles, protected admins can't be demoted, and the last admin can't be
  demoted or deleted, even under concurrency (all tested).
- **Rate limits:** login (10 per 15 min per account, 50 per IP), registration,
  resend and forgot-password, unchanged.

## 4. Storage architecture

Unchanged, because Supabase Storage was never used. Manuscripts, revised
manuscripts and published PDFs live under `MANUSCRIPT_STORAGE_DIR`. This is a
private directory outside the app and the web root, with random 128-bit
filenames, mode 0600 and a path-traversal guard. Uploads are checked by magic
bytes (PDF/DOCX/DOC) and limited to 25 MB. Every download goes through a route
that re-checks ownership, assignment and released version (double-blind), or,
for the public archive, that the publication, issue and volume are all
published and `manuscript_public` is set. **No file needs to move.**

## 5. Data migration status

- **Source.** Exported read-only from Supabase on 2026-11-04
  (`scripts/migration/export-supabase.mjs`). It holds 3 users (2 administrators,
  1 student), 2 `ADMINISTRATOR` role rows, and **0 rows** in every workflow
  table. The file is kept outside the repository in `../rpp-migration-backups/`.
- **Into the shared DB.** `research_users` starts empty there, so every account
  is inserted with its **current (Supabase) UUID**, and the roles are restored
  with `isAdmin` kept in sync. The import is a dry run by default, and it is
  idempotent: re-running it changes nothing.
- **Passwords.** Supabase password hashes aren't exposed through its API, so
  after the import nobody has a password. Either:
  (a) admins run `npm run db:set-password -- "<email>"` and users use **Forgot
  password**, or
  (b) export `select id, encrypted_password from auth.users` in the Supabase SQL
  editor and pass it to the import with `--hashes <file>`. The bcrypt hashes are
  then upgraded to Argon2id on first login.
- **Local rehearsal.** Done on the local XAMPP database: read-only status, then
  preflight, migrate and import. The 18 `research_*` tables were created, and the
  database's other tables were left untouched.

## 6. Production runbook (shared cPanel database; your action — not executed)

1. **Credentials.** Put the database settings in the server `.env` (and in local
   `.env.local` if you want me to inspect from here):
   `DB_HOST=65.1.118.10`, `DB_PORT=3306`,
   `DB_USER=atlasuniversitye_employment_user`, `DB_PASSWORD=<existing>`,
   `DB_NAME=atlasuniversitye_employment_survey`, `DB_CONNECTION_LIMIT=10`,
   `DB_QUEUE_LIMIT=0`, `DB_CONNECT_TIMEOUT_MS=10000`. Remove the old `DB_PASS`
   line (it is only a fallback). If the host refuses the connection, add the
   app server's IP under **cPanel → Remote MySQL**.
2. **Inspect (read-only).** Run `npm run db:check`. It lists every table in the
   database (names only), shows RPP's `research_*` tables with row counts, and
   runs the **collision preflight**. Send me the output before going further.
3. **Back up.**
   - Whole database, so the Employment Survey data is covered too:
     `mysqldump --single-transaction --no-tablespaces -h 65.1.118.10 -u atlasuniversitye_employment_user -p atlasuniversitye_employment_survey > /var/backups/rpp/pre-rpp-$(date -u +%Y%m%dT%H%M%SZ).sql`
     (or use cPanel → Backup → download the MySQL database).
   - Later, RPP-only backups: `npm run db:backup -- /var/backups/rpp` (exactly
     the 18 `research_*` tables).
4. **Migrate (needs your explicit go).** Run `npm run db:migrate` (read-only
   status and preflight), then `npm run db:migrate -- --apply`.
5. **Import.** Copy the export JSON to the server (`scp`; it contains personal
   data). Run `npm run db:import-supabase-export -- <file>` as a dry run, review
   the output, then repeat with `--apply`. Afterwards, `shred -u <file>`.
6. **Remaining environment.** Keep `NEXT_PUBLIC_SITE_URL`,
   `MANUSCRIPT_STORAGE_DIR`, `STUDENT_CHECK_API_KEY`, `EMAIL_ID` and
   `EMAIL_APP_PASSWORD`. Add `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and
   `GOOGLE_REDIRECT_URI`. Remove every `SUPABASE_*` variable.
7. **Admin passwords.** `npm run db:set-password -- "<email>"`.
8. **Switch over.** `npm run build`, then `pm2 reload <app>`, then check
   `/api/health` and sign in.
9. **Keep the Supabase project untouched** until production has been verified.

`.github/workflows/researh.yml` auto-deploys on every push to `main`, so finish
steps 1–7 **before** pushing.

## 7. Tests

- `npm run test:mysql` creates its own throwaway database on a **local** server
  (it refuses remote hosts), applies the real migrations, and covers:
  shared-database collision safety, prefix conventions, auth, sessions, tokens,
  roles and the full workflow state machine. It then drops that database.
- Offline suites: `npm run test:<name>`.
- HTTP suites against a running build: see `staging-validation-plan.md`.
